# v1.2.1 — CPU power decode fix

CPU power readings were stuck around 4 W regardless of actual draw. The catalog probe was picking `PCPT` (whose dataType is `spa5`, a format we didn't decode), and the decoder was silently falling through to `byte[0]` as UI8 — returning meaningless small integers.

- **CPU power preference reordered**: `PCPR` → `PCTR` → `PCPT` → `PCPC` → `PCAM` → `PC0R` → `PC0C`. `PCPR` is the Intel RAPL-equivalent total and matches reality (~8 W idle, ~50 W moderate, ~125 W full TDP on a 10-core iMac).
- **New generic SP-family decoder**: `Decoders.decodeSPFixedPoint(b0, b1, dataType)`. Pattern `spXY` = X integer bits, Y fractional bits, value = `signed_int16(b0, b1) / 2^Y`. Handles `sp78`, `spa5`, and any future SP variant uniformly.
- **`decodePower` no longer falls back to UI8** for unknown dataTypes — byte-0-as-watts has no physical meaning. nil return makes the catalog skip the key.
- **Power-probe diagnostic dump** at every helper start: one stderr line per known power SMC key with key, dataType, raw bytes, decoded value. Captured in the plugin log; grep `power-probe` to triage a wrong reading on a new Mac model. Compare with `sudo powermetrics --samplers cpu_power -n 1 -i 1000` for ground truth.

167 tests green (86 Swift + 81 TS).
